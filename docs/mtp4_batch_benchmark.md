# MTP-4 batch size 扩展测试

2026-09-21 在 RTX 3090 上实测。模型参数量为 3,725,772，序列长度为 2048。只改变 global batch 和 micro batch，保持模型、四头等权损失、训练文件、窗口索引、Adam 配置、梯度裁剪及 BF16 精度不变。学习率仍按原来的 2,000 步预热、50,000 步调度运行，没有按 batch 放大学习率。

每档在独立进程中使用相同随机种子重新初始化模型和优化器，运行 120 次梯度更新；前 20 步作为性能预热，后 100 步计时。预热步骤也正常训练。每步耗时包含取数据、前向计算、四头损失、反向传播和优化器更新，并在计时边界同步 GPU；不含验证、保存和首次编译时间。测试只写指标，没有保存 checkpoint，也没有修改正式训练的 checkpoint 逻辑。

| batch size | 是否成功 | 峰值显存（GB） | 平均 step 时间 | 备注 |
| ---: | --- | ---: | ---: | --- |
| 32 | 是，120 步 | 5.676 | 120.204 ms | GPU 利用率 99.09%；loss 5.5445 → 4.4446 |
| 64 | 是，120 步 | 11.283 | 235.864 ms | GPU 利用率 99.58%；loss 5.5445 → 4.4581 |
| 128 | 否，显存不足 | 22.468* | — | 未完成首次梯度更新，Triton 报 CUDA 显存不足 |
| 256 | 否，显存不足 | 23.233* | — | 未完成首次梯度更新，PyTorch 报 CUDA 显存不足 |

显存采用 PyTorch 峰值分配量，单位为十进制 GB，与原实验的 5.676 GB 一致。带 * 的数值只是失败前峰值，并不代表该 batch 完整运行所需显存。32、64 的峰值预留显存分别为 6.130、12.161 GB。每约 0.5 秒通过 nvidia-smi 采样一次，32、64 在计时区间分别获得 23、45 个样本；GPU 利用率是整卡采样均值。整卡显存采样峰值分别为 8,240、14,049 MiB，包含桌面、CUDA 上下文等开销，与 PyTorch 分配量口径不同。

loss 为前 10 步和最后 10 步总损失的均值。成功运行的两档均下降，所有步骤的 loss 和梯度范数均为有限值。这只说明短时训练正常，不用于比较不同 batch 的模型性能。

## 效率与建议

32、64 的吞吐率分别为 545,206、555,709 个输入字节位置/秒。64 相对 32 提高约 1.93%，显存分配量约翻倍。单次短测没有估计测量误差，不能据此认定存在稳定、显著的加速。

建议后续训练采用 **global batch 64、micro batch 64**：它是本次指定四档中最大成功值，显存仍有余量，短测吞吐率略高。若优先保持既有训练条件，batch 32 的计算利用率已经很高，继续使用也合理。未测试 65–127，因此 64 不是精确显存容量上限。

本项目在单 GPU 上满足：global batch = micro batch × 梯度累积次数。本次每档二者相等，累积次数都是 1，实际每次梯度更新使用 32、64、128、256 条序列（后两档因显存不足未完成更新）。batch 64 每次成功更新处理 131,072 个输入字节位置。

正式训练入口当前只有 micro batch 参数，全局 batch 默认固定为 32；仅传入 micro batch 64 会因配置校验失败而退出。后续启用 batch 64 需要同时配置 global batch 64。现有 1,600,000 条窗口索引在 batch 64 下只够 25,000 次更新；若仍要求 50,000 次更新，必须另行确定如何复用原训练窗口。恢复已有 checkpoint 还会校验 batch 配置，因此不能直接以更大 batch 恢复原目录。这些长期训练调整不属于本次短测，未修改。
